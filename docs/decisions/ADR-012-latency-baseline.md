## 2. 测量口径（关键，最容易算错）

`t` 与 `timings.*` 都是 sidecar 单调时钟的**绝对刻度**（自进程启动起算，3.4），
不是「本段耗时」。分段必须做差，起点用同轮的 `state(generating).t`：

```
首 token      = llm_first_token_ms - state(generating).t
首 token→音频 = tts_first_audio_ms - llm_first_token_ms
turn 总耗时   = total_ms            - state(generating).t
```

`state(generating)` 每轮必发，所以任何客户端都能算，无需给 `Timings` 加字段
（改冻结协议要走 12.2 变更记录）。

`turn_complete.timings` 的 `n` 可能小于轮数：FAILED/CANCELLED 没有首音频，
该段留空不参与统计——**不许记成 0ms**，那会让超预算看起来像达标。

## 4.1 真机整链（2026-10-24，本机 GPU，TTS 侧）

环境：Windows；部署实际使用的 `sidecar/.venv`（torch 2.7.1+cu126，CUDA 可用）；
`~/.cache/echoes/models/CosyVoice2-0.5B` 权重就位；`llm=mock`（固定回复 21 字）、
`asr=mock`、`--ws off`（消息面口径，见 §3 尾注）。
命令：`python scripts/bench_latency.py --turns 5 --tts cosyvoice2`。

| 段 | 预算 | 修复前 P50 / P95 | 修复后 P50 / P95 | 判定 |
| --- | --- | --- | --- | --- |
| 输入 → 首 token | ≤700ms | 0 / 1 | 0 / 1 | —（mock LLM，此段无意义） |
| 首 token → 首音频 | ≤500ms | 4211 / 5195 | **2727 / 3194** | ❌ 超 5.5× |
| turn 总耗时 | ≤2500ms、P95 ≤4000ms | 4211 / 6065 | 4705 / 5932 | ❌ 超 1.9× / 1.5× |

报告：`_bench_out/latency_20261024_105459.md`（修复前）、`_bench_out/latency_20261024_110756.md`（修复后）。

**「修复前 → 修复后」改的到底是什么**：`synthesize` 原来为了「让末段带 is_final」而
**扣住一个 chunk**（等下一个到达才吐），于是首音频要等**第二个** chunk——38 字文本
实测首段 2.7s 就好了，TTFA 却记成 7.7s。改成「真 chunk 产出即发 + 零长度 `is_final`
帧收尾」（协议既有形态：壳侧 PTT 松手也是空 `is_final` 帧收束，`push_pcm16` 对空样本
直接 return）后，引擎级 TTFA **7.7s → 2.7s**，整链 **4.2s → 2.7s**。
代价：端到端 4.2s → 4.7s（逐段发送多约 0.5s），换早 1.5s 出声。

**引擎级成本形状**（同进程、warmup 后；`_bench_out/probe_shape.log`，修复前口径）：

| 文本 | 音频时长 | TTFA | RTF |
| --- | --- | --- | --- |
| 4 字 | 1.1s | 1.6–2.6s | 1.4–2.4 |
| 9 字 | 2.3s | 2.3–2.8s | 1.0–1.23 |
| 14 字 | 3.4s | 3.2–3.4s | 0.93–0.96 |
| 23 字 | 5.4s | 4.4–5.3s | 0.83–0.99 |

拟合：**TTFA ≈ 1.4s 固定开销（文本前端 + prompt 特征 + 首块 vocoder）+ 0.65 × 音频秒数**。

**首句短切 A/B**（38 字单句，修复后口径；`_bench_out/probe_cut2.log`）：

| 配置 | 首句切法 | TTFA | turn 总 |
| --- | --- | --- | --- |
| A 不短切 | 整句 38 字 | 6054 / 6250ms | 7779 / 8058ms |
| B 短切 20 字 | 12 字 + 26 字 | **2729 / 2744ms** | 7647 / 7460ms |

→ 首句短切 **-55% TTFA**，总时长不变差。这就是 `split_sentences(first_max_chars=20)`
默认开启的依据（ADR-009 的 4.5 分句策略由引擎注入）。

**三级就绪实测**：`hello.engines[tts].ready` 翻转在进程启动后 **36.1s**（首次、
文件系统缓存冷）与 **21.6s**（重跑、缓存热）；其中引擎 `warmup()` 本身 20.2–22.8s，
其余是 vendored/torch 导入 + onnxruntime CUDA EP + wetext 快照校验。
预算 25s → **冷启 ❌（1.44×）/ 热启 ✅**。

## 4.2 判定（按 §7 规则）

三段全红且远超 20% → **§7.3 生效：不许改预算**。已做的优化见 §5，仍然够不到，
因此这不是「调预算」的问题，是**产品口径要重新决定**（见 §9）。

## 5. 本次关于 TTFA 的工程动作（已实测，结论可引用）

| # | 动作 | 实测效果 |
| --- | --- | --- |
| 1 | 音色特征缓存（`_register_voices`，warmup/clone 时注册一次） | 每轮省一次 campplus 嵌入 + speech tokenizer（百毫秒级，未单独计时） |
| 2 | 逐句合成（`split_sentences` 接线） | 让第 3 项成为可能（否则整段一句，无可切） |
| 3 | **流式不再扣帧**（零长度 `is_final` 收尾） | 引擎 7.7s→2.7s，整链 4.2s→2.7s（§4.1） |
| 4 | **首句短切 20 字**（`first_max_chars`） | TTFA -55%（6.1s→2.7s），总时长不变差（§4.1） |

第 1、2 项在本轮之前已落地；3、4 是本轮实测驱动出来的——**先量后改**，顺序不能反。

## 7. 校准决策规则（预先约定，避免事后找理由）

1. 实测全绿 → **下调**明显宽松的项（例如首 token 实测 120ms，则预算降到 300ms 量级），
   记入本文档并同步母文档 6.2 表。
2. 单段超预算 ≤20% → 允许一次性校准（这是母文档给的额度），但要在本文档写清
   「为什么这 20% 是实现约束而非偷懒」。
3. 超预算 >20% → **不许改预算**，必须走优化路径（预热顺序 / 分句粒度 / 流式 chunk /
   模型档位），优化后重测。

## 9. 预算缺口的处置建议（需产品/母文档决策，不得由实现方自行改）

三段实测距预算：首音频 2727ms vs 500ms（5.5×）、端到端 4705ms vs 2500ms（1.9×）、
冷启就绪 36.1s vs 25s（1.44×）。按 §7.3 不改预算，可选路径与代价：

| # | 路径 | 预期收益 | 代价 / 风险 |
| --- | --- | --- | --- |
| 1 | **开场语气词预合成缓存**：预热时把「嗯，」「让我想想」等 3–5 个短应答音预先合成，首个 LLM token 到达即播缓存，同时后台合成正文 | 感知首音频 ≈ 0–300ms（**唯一能进 500ms 量级的路径**） | 需编排层/壳侧支持「预置语音段」；语气词与回复内容可能不搭（产品观感要试听） |
| 2 | 提高 RTF：TensorRT / JIT / 更小模型档位（ADR-014 属） | RTF 0.85→0.3 量级，TTFA 仍受 ~1.4s 固定开销约束 | 工程量与兼容性大；固定开销仍进不了 500ms |
| 3 | 冷启 36.1s：权重预转格式（bin→safetensors/ORT）、预热顺序重排、推迟非必需扩展 | 目标 ≤25s | 需重跑打包与升级路径 |
| 4 | 按实测校准预算（首音频 ≤3s、端到端 ≤5s、就绪 ≤40s） | 立刻可判绿 | **改的是验收契约**，必须走母文档 6.2 变更记录并说明「本地 0.5B 模型的物理下界」 |

实现方的建议：4 先落地把验收口径定成可实现值，同时把 1 作为阶段 2 的交互优化项
排期（它是唯一能让**体感**达标的路径，且与模型档位无关）。
